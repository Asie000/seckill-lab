# seckill-lab 完整压测报告

**日期**：2026-10-10
**项目**：电商大促综合实验（读侧性能优化 + 写侧秒杀高并发）
**报告口径**：所有数据为**真机实测**（JMeter + MySQL/Redis 自身统计），单机同机压测，**只做相对对比**，不宣称绝对 QPS 上限。

---

## 0. 一句话结论

把一个「电商大促」系统从**慢、错、脆**做到**快、对、稳**：
- **读侧**：N+1 消除（3.3x）、SQL 日志移除（14x）、缓存（1.4x）、异步（3.7x）；
- **写侧**：从超卖+重复下单，做到不超卖、不重复、能削峰、能对账、能限流、能自动关单；
- **最大收获**：踩到并修复 **3 个真实 bug**（SQL 日志瓶颈、缓存一致性脏读、限流被绕过），外加 2 个 Kafka 真 bug（生产端配置、毒消息阻塞）。

## 2. 关键配置

### 2.1 应用配置（`application-dev.yml`）

```yaml
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/seckill?...&rewriteBatchedStatements=true
    hikari:
      maximum-pool-size: 30     # r0 为 10；r2 调到 30
      minimum-idle: 10
      connection-timeout: 3000
  data:
    redis: { host: localhost, port: 6379, timeout: 3000ms }
  kafka:
    bootstrap-servers: localhost:9092
    listener:
      ack-mode: manual          # v3：消费者手动 ack
    producer:
      acks: all
      retries: 3
      properties:
        max.block.ms: 3000
        request.timeout.ms: 3000     # ★ 必须配，且 <= delivery.timeout.ms
        delivery.timeout.ms: 5000
    consumer:
      group-id: seckill-lab
      auto-offset-reset: earliest
```

- `@Async` 线程池：**core 16 / max 64 / queue 500 / CallerRunsPolicy**。
- Tomcat 使用默认（`threads.max=200`）。

### 2.2 压测协议（重要）

| 项 | 取值 |
|---|---|
| **SQL 日志** | 压测统一**关闭**（`--mybatis-plus.configuration.log-impl=...NoLoggingImpl`）—— 因为开日志会掩盖一切（14x） |
| 并发梯度 | **100 / 200 / 500 / 1000** 线程 |
| 加压方式 | ramp-up 10s，持续 30s（部分健康检查用 20s） |
| JMeter 堆 | `-Xms1g -Xmx2g`（D 盘不可写，用 `$env:HEAP` 覆盖） |
| JMX 参数化 | `${__P()}` 在 ThreadGroup 无效 → 改用 `@THREADS@/@RAMP@/@DURATION@` 占位符 + PowerShell 替换 |
| 拓扑 | **应用与 JMeter 同机**，故结论只做相对对比 |

### 2.3 运行时开关（`scripts/app.ps1`）

```
-Pool N                  # HikariCP 连接池大小
-NoSqlLog                # 关 SQL 日志（压测必开）
-CacheOff / -MultiLevelOff / -Penetration none|null|bloom / -L1MaxSize N / -Breakdown off|mutex|logical
-KafkaOff / -AsyncOff / -RateLimitOff / -Fallback index|lock
-ConsumerGroup X / -ConsumerLatest
-AutoCloseOff / -AutoCloseIntervalMs / -AutoCloseTimeoutSec / -AutoCloseBatch / -AutoClosePerOrder
```

## 5. 缓存深化（r5~r7）

### 5.1 r5 缓存击穿（互斥锁 vs 逻辑过期）

场景：热点 key，TTL 2s，慢查询 200ms，各档 30s。

**真实回源 DB 次数（核心指标）**

| 并发 | off 无保护 | mutex 互斥锁 | logical 逻辑过期 |
|---:|---:|---:|---:|
| 100 | 1168 | **14** | 27 |
| 200 | 2144 | **14** | 26 |
| 500 | 2563 | **14** | 41 |
| 1000 | **2650** | **14** | 70 |

吞吐三档均 26k~32k/s（都命中缓存），**区别全在回源次数**。

### 5.2 r6 / r6b 多级缓存（Caffeine + Redis）

工作集 21 个商品、随机访问，30s：

| 模式 | 并发 | 吞吐 | 真实 Redis GET（实测） |
|---|---:|---:|---:|
| 多级 L1+L2 | 100~1000 | 32k~51k/s | **126**（四档相同） |
| 仅 Redis | 100~1000 | 27k~33k/s | 824,020~990,393 |

- **吞吐约 1.6x**，**Redis 负载降约 7000x**（用 `redis-cli INFO commandstats` 实测，非应用估算）；
- L1 容量压到 5：真实 Redis GET 涨到 ~19 万（~1500x）；
- 发现「单飞效应」：单线程命中 23.66%（≈5/21），200 线程 86%（并发共享加载）；
- **一致性 bug**：多级缓存单实例也会脏读，延迟失效修复。

### 5.3 r7 缓存穿透 + 布隆过滤器

场景：请求不存在的 id 100000~100999，DB 负载用 **MySQL 自身 `Com_select`** 实测。

| 策略 | 并发 | 吞吐 | **DB 查库次数** |
|---|---:|---:|---:|
| none 无防护 | 100~1000 | ~22k/s | **664,584~684,636** |
| null 缓存空值 | 100~1000 | ~28k/s | **~1000** |
| bloom 布隆过滤器 | 100~1000 | ~28k/s | **0** |

布隆用 **Redis bitmap**（m=100000，k=3），拦截 ~83万~89万次。

## 6. 组件与可靠性补充（r8~r12）

| tag | 内容 | 关键实测 |
|---|---|---|
| **r8** | 分布式 ID（时间戳<<32 \| Redis 自增） | 10 万并发 ID **0 重复**，**64,977 ID/s**；HTTP 层 29,574/s；UUID 对照 478,468/s 但不可排序 |
| **r9** | 秒杀加库存（幂等 + 先DB后Redis + INCRBY） | 并发补货与扣减对账 **5001=5001**，redis==db；顺带修 **2 个 Kafka 真 bug**（见 §7） |
| **r10** | Kafka 顺序 / 堆积 / offset | keyed 乱序 **0**；unkeyed 2000 条乱序 4、20000 条乱序 **2404**；灌 12000 条(0.2s) → lag 12000 → 10s 后 6848(≈515/s) → 恢复后 **0** |
| **r11 / r11b** | 未支付订单到期自动关闭（Spring Task） | 10005 单三次扫完；**逐单 20358ms → 批量回补 9327ms（2.2x）**；索引 `range` vs 全表 `ALL`；关完 redis==db |
| **r12** | 删缓存失败 → Kafka 补偿重试 | 模拟删除失败：DB=777.77 而缓存仍 888.88(脏) → 补偿消费者删除 → 5s 后缓存 777.77(一致) |

## 7. 五个真实 Bug（最有价值）

| # | Bug | 现象 | 根因 | 修复 |
|---|---|---|---|---|
| 1 | **SQL 日志隐藏瓶颈** | 吞吐卡 ~100/s | `StdOutImpl` 每请求打印全部 SQL | 关闭后 **95.7→1387/s（14.5x）** |
| 2 | **缓存一致性脏读** | `stale=true` | 删缓存 + 并发回填旧值 | 延迟双删 → `stale=false` |
| 3 | **限流被 member 撞车绕过** | 设定 500/s 实测放行 1370/s | `math.randomseed(now)` 同毫秒同 member，ZSet 去重致 ZCARD 少算 | member 传 UUID → 512/s |
| 4 | **Kafka 生产端配置错误** | 秒杀恒 500 | 只配 `delivery.timeout.ms=5000` 未配 `request.timeout.ms`（默认 30000），producer 构造即失败 | 补 `request.timeout.ms=3000` |
| 5 | **毒消息永久阻塞分区** | 消费者卡死、订单增量为 0 | 失败不 ack → seek 重试同一条，无限循环 | `DefaultErrorHandler` + 死信队列 `seckill-order-dlq`（重试 2 次/200ms） |

## 9. 面试速查（一句话）

- **N+1**：trace 识别 → 批量 `IN` → 62→5 次 SQL，3.3x。
- **连接池**：`核数*2+磁盘`，「不是越大越好」，梯度实验证伪。
- **SQL 日志**：`StdOutImpl` 隐藏 14x 开销，压测必关。
- **缓存**：Cache-Aside；穿透（布隆/空值）、击穿（互斥/逻辑过期）、雪崩（TTL 随机）、一致性（延迟双删/MQ 补偿）。
- **多级缓存**：Caffeine+Redis，吞吐 1.6x、Redis 负载降 ~7000x。
- **秒杀**：`WHERE stock>=1`、Redis+Lua 预扣、一人一单、Kafka 削峰、状态机乐观锁、超时关单。
- **消息可靠性**：手动 ack、幂等消费、死信队列、发送失败回调。
- **限流**：滑动窗口（ZSet）、令牌桶、AOP 注解、维度 IP/USER。
- **性能方法论**：先基线 → 排除法定位（应用→中间件→DB）→ 对照实验 → 数据说话。

## 10. 已知不足

- 单机同机压测，结论只做相对对比；
- 生产端未做**本地消息表/事务消息（Outbox）**；
- 应用启动对 Kafka 强依赖（Kafka 不在会卡启动）；
- **库存分桶**未实现；缓存雪崩（TTL 随机）未单独实验；
- Rebalance/ISR 因单节点单副本无法实测；
