# r1-n1 —— 批量 IN 查询消除 N+1

**tag**：`r1-n1`
**日期**：2026-10-10
**主题**：把订单列表的 for 循环补查改成批量 `IN` 查询。

---

## 1. 目标

`r0-baseline` 里一次 20 行列表打 **62 次 SQL**（1+3×20+1分页），把所有数据库连接占满。
本版把三条补查合并为批量查询，目标：**62 → 5 次**（业务查询 61 → 4）。

---

## 2. 代码变更

### 2.1 `OrderServiceImpl.toVoBatch()`（新增，核心）

替换原来的 `toVoNaive()`（后者仅保留给订单详情的单条查询用）：

```java
private List<OrderVO> toVoBatch(List<Order> orders) {
    Set<Long> userIds = orders.stream().map(Order::getUserId).collect(Collectors.toSet());
    List<Long> orderIds = orders.stream().map(Order::getId).collect(Collectors.toList());

    // 补查 1：用户（1 次）
    Map<Long, User> userMap = userMapper.selectBatchIds(userIds).stream()
            .collect(Collectors.toMap(User::getId, Function.identity()));
    // 补查 2：明细 + 商品名（1 次 IN）
    Map<Long, List<OrderItemVO>> itemMap = orderItemMapper.selectByOrderIdsWithGoods(orderIds).stream()
            .collect(Collectors.groupingBy(OrderItemVO::getOrderId));
    // 补查 3：物流（1 次 IN）
    Map<Long, OrderLogistics> logisticsMap = orderLogisticsMapper.selectList(
            new LambdaQueryWrapper<OrderLogistics>().in(OrderLogistics::getOrderId, orderIds))
            .stream().collect(Collectors.toMap(OrderLogistics::getOrderId, Function.identity(), (a, b) -> a));

    return orders.stream().map(order -> { /* 用 map 在内存里拼装 */ }).collect(Collectors.toList());
}
```

### 2.2 新增批量查询

| 文件 | 变更 |
|---|---|
| `OrderItemVO` | 增加 `orderId` 字段（批量查回后按 orderId 分组） |
| `OrderItemMapper` + `.xml` | 新增 `selectByOrderIdsWithGoods(List<Long>)`，用 `<foreach>` 拼 `IN` |
| `OrderLogisticsMapper` | 复用 `BaseMapper.selectList` + `LambdaQueryWrapper.in`，无需 XML |
| `UserMapper` | 复用 `selectBatchIds` |

## 3. 证据：SQL 次数 62 → 5

一次 `GET /api/order/list?pageNum=1&pageSize=20`，统计 `app.log`：

```
SQL 总数: 5
1  SELECT COUNT(*) AS total FROM orders                 -- 分页计数
1  SELECT id,order_no,user_id,order_type,... FROM orders -- 订单分页
1  SELECT id,username,nickname,create_time FROM user WHERE id IN (...)
1  SELECT oi.order_id...,g.name FROM order_item oi LEFT JOIN goods g ... WHERE oi.order_id IN (...)
1  SELECT id,order_id,company,... FROM order_logistics WHERE order_id IN (...)
```

**业务查询 4 次**（订单 + 用户 + 明细 + 物流），比 r0 的 61 次下降 **93%**。

## 5. 结论

1. **吞吐提升约 5 倍**（19 → 93 req/s），**延迟下降 4~5 倍**（1000 并发平均 38.1s → 9.3s）。
2. **并发仍然不改变吞吐**：100~1000 并发下吞吐都稳在 ~93/s。
   → N+1 修掉后，瓶颈已经**换人**：现在是 **Hikari 只有 10 个连接**在限制吞吐。
   这正是下一版 `r2-pool` 要验证的假设。
3. 修 N+1 = 把每请求 62 次数据库往返压到 5 次，相同连接数能服务的吞吐自然成倍上升。

## 6. 遗留问题 / 下一步

- `IN` 子句在 ID 数量极大时的上限问题（当前每页仅 20~100 个 ID，暂不触发）。
- 读侧仍无缓存，商品信息每次回表 → `r3-cache`。
