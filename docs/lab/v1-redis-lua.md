# v1-redis-lua —— Redis + Lua 预扣 + 一人一单 + 双兜底

**tag**：`v1-redis-lua`
**日期**：2026-10-10
**主题**：用 Redis + Lua 同时治超卖与重复下单，并把库存/活动信息搬到 Redis。
**标准口径**：日志关闭。

---

## 1. 代码与数据变更

### 1.1 数据：唯一索引兜底

`orders` 增加唯一索引（兜底方案 A）：

```sql
UNIQUE KEY `uk_activity_user` (`activity_id`, `user_id`)
```
普通单 `activity_id` 为 NULL，MySQL 唯一索引允许多个 NULL，不受影响。

### 1.2 Lua 脚本 `resources/seckill.lua`

一次性原子完成「库存判断 + 一人一单 + 扣减」：

```lua
local stock = tonumber(redis.call('get', stockKey)) or 0
if stock <= 0 then return 1 end                       -- 库存不足
if redis.call('sismember', orderKey, userId) == 1 then return 2 end  -- 重复
redis.call('decr', stockKey)
redis.call('sadd', orderKey, userId)
return 0
```

### 1.3 秒杀服务 `SeckillServiceImpl`

主链路：
1. **活动信息读 Redis hash**（`seckill:activity:{id}`），不再每请求查 DB；
2. 执行 `seckill.lua`；
3. 通过后落库：DB 原子扣减 + 写 `orders`/`order_item`/`stock_log`。

**兜底双方案**（`seckill.fallback` 切换）：
- `index`（默认）：靠唯一索引 `uk_activity_user`，重复插入抛 `DuplicateKeyException` → 返回 1004；
- `lock`：先用 Redis `SETNX` 锁 `lock:seckill:{activityId}:{userId}`，拿不到锁即判重复。

重复命中兜底时会**补偿 Redis**（把 Lua 扣掉的库存加回、把用户从集合移除）。

### 1.4 预热接口

`POST /api/seckill/{activityId}/warmup`：把 DB 库存写入 `seckill:stock:{id}`、清空 `seckill:order:{id}`、缓存活动信息。**压测前必须调用。**

## 3. 压测数据（30s，日志关闭，库存 100，随机用户）

运行流程：`reset-stock.sql` → `warmup` → JMeter。

| 1000 | 3691.8/s | 227.6ms | 272 | 288 |

### 3.2 活动信息也缓存到 Redis（最终版）

| 并发 | 吞吐 | 平均 | P95 | P99 |
|---:|---:|---:|---:|---:|
| 100 | 3900.9/s | 21.4ms | 29 | 36 |
| 200 | 4043.0/s | 41.4ms | 57 | 64 |
| 500 | 4047.3/s | 103.6ms | 130 | 146 |
| 1000 | 3973.5/s | 211.3ms | 254 | 279 |

> 把"每请求查活动表"改成读 Redis 后，吞吐 **+5~8%**。
> 说明：**光做 Redis 预扣还不够，只要请求路径上还留着一次 DB 读，DB 就仍是隐性瓶颈。**

### 3.3 兜底方案 A/B（200 并发）

| 兜底方案 | 吞吐 | 平均 | P99 |
|---|---:|---:|---:|
| `index`（唯一索引） | 4043.0/s | 41.4ms | 64 |
| `lock`（Redis SETNX 锁） | 3771.8/s | 44.4ms | 75 |

锁方案略慢（每次成功多 2 次 Redis 操作），但两者都正确。锁的价值在更复杂的临界区，
本场景"一人一单"用唯一索引更轻。

## 4. 业务正确性对账

两种兜底方案各自跑完后：

| 方案 | 剩余库存 | 订单数 | 重复下单用户数 |
|---|---:|---:|---:|
| index | 0 | 100 | 0 |
| lock | 0 | 100 | 0 |

- **不超卖**：库存恰好 0，订单恰好 100。✅
- **无重复**：重复下单用户数 0。✅
- 对账 ①②③ 全部 PASS。

对比：

| 指标 | v0a | v0b | v1 |
|---|---|---|---|
| 超卖 | ❌ -10893 | ✅ 0 | ✅ 0 |
| 重复下单 | ❌ 3199 人 | ❌ 仍存在 | ✅ 0 |
| 吞吐 | ~330/s | ~340/s（真实） | ~4000/s |

> 注意 v1 的 ~4000/s 和 v0b 库存耗尽后的 ~3700/s **口径不同但不能直接说"提升 10 倍"**：
> 两者都是"大量请求被快速拒绝"的场景。v1 的价值在于：
> ① 两个病都治好；② 拒绝路径完全不碰 DB（Redis 内完成）；
> ③ 在 DB 压力更高的场景下，优势才会随并发放大（本机 ~4000/s 的天花板由应用/HTTP/Redis 往返决定，掩盖了这一点）。

## 5. 结论

1. **Redis + Lua 一次性治好了超卖和重复下单**（v0b 只治前者）。
2. **预热是硬前提**：不 warmup 则 Redis 库存 key 不存在，所有请求直接库存不足。
3. **活动信息也要缓存**：否则每请求一次 DB 读会把 Redis 预扣的收益吃掉一部分。
4. **唯一索引 vs 分布式锁**：本场景唯一索引更轻；锁适合更复杂的临界区。
5. 吞吐在单机实验里被 ~4000/s 的天花板限制，v1 相对 v0b 的提升不显著，
   但**正确性**和**把 DB 从拒绝路径摘除**是实打实的。
