# seckill-lab 电商大促综合实验 —— 总报告

**日期**：2026-10-10
**范围**：Phase R 读侧（r0~r4）+ Phase S 写侧（v0a~v4）
**标准口径**：压测统一**关闭 SQL 日志**（原因见专题）；单机实验，仅作**相对对比**。

---

## 1. 一句话结论

一个"电商大促"系统，平时读多写少、整点秒杀写热点。本实验把它从"慢、错、脆"一步步做到"快、对、稳"：

- **读侧**：N+1 消除（3.3x）、SQL 日志移除（14x）、缓存、异步。
- **写侧**：从超卖+重复下单，做到不超卖、不重复、能削峰、能对账、能限流。
- **最大的收获不是某个版本，而是踩到并修复了三个真实 bug**：
  SQL 日志瓶颈、缓存一致性脏读、**限流被 member 撞车绕过**。

## 3. Phase R 读侧 —— 逐版贡献与代价

| 版本 | 改动 | 关键结果 | 代价 / 说明 |
|---|---|---|---|
| **r0** | N+1 订单列表 + 小连接池 + 同步下单 | 订单列表 **~420/s**（日志关）；单请求 **62 次 SQL** | 基线 |
| **r1** | 批量 IN 消除 N+1 | **~1370/s**（**3.3x**）；SQL 62→5 | 内存拼接略复杂 |
| **r2** | 连接池 10→30 | **无提升**；反而逼出真凶：SQL 日志 | 连接池 10~50 无差异 |
| **r3** | Redis 缓存商品 | 商品读 21k→**31k/s**（~1.4x） | **引入缓存一致性脏读**（见 §5） |
| **r4** | @Async 拆非核心逻辑 | 下单 28→**104/s**（3.7x），P50 1623→**23ms** | 线程池有容量上限，队列满退化为同步 |

**专题：SQL 日志开销（14x）**
`mybatis-plus.configuration.log-impl=StdOutImpl` 让每请求把所有 SQL 打印到 stdout。
200 并发下：日志开 95.7/s → 日志关 **1387/s**（**14.5x**）。它一度掩盖了所有优化的差异。
→ 结论：**压测必须关 SQL 日志**；开发调试照常开。

## 4. Phase S 写侧 —— 逐版贡献与代价

| 版本 | 改动 | 正确性 | 吞吐 | 代价 / 说明 |
|---|---|---|---|---|
| **v0a** | 无保护扣减 + 无幂等 | ❌ 超卖（库存 -10893）+ ❌ 重复（3199 人） | ~330/s | 基线（病灶） |
| **v0b** | 加 `WHERE stock>=1` | ✅ 不超卖（库存 0/订单 100）；❌ 仍重复 | ~340/s | 真吞吐（放大库存后） |
| **v1** | Redis+Lua 预扣 + 一人一单 + 双兜底 | ✅ 不超卖 ✅ 不重复 | **~4000/s** | 预热是硬前提；活动也要缓存 |
| **v2** | Kafka 异步落库 | ✅ 同上 | 成功路径 **~7.7x**（vs 同步） | 可靠性变"裸"，需 v3 |
| **v3** | 幂等消费 + 手动 ack + 支付乐观锁 + 超时关单 | ✅ 并发支付仅 1 次成功；关单回补正确 | ~4000/s（不变） | 可靠性在消费者侧 |
| **v4** | 滑动窗口限流 500/s | ✅ 放行 ~512/s | 总处理不降，超出挡 429 | 弃车保帅 |

> v1/v2/v4 的 ~4000/s 与 v0 的"快速拒绝"口径不同，不能简单说"提升 10 倍"；
> 需要看**成功路径**与**正确性**。

## 5. 三个真实 Bug（最有价值的部分）

### Bug 1：SQL 日志是隐藏瓶颈（14 倍）
r1 之后吞吐卡在 ~100/s，一度误判为"连接池瓶颈"。
r2 做连接池梯度（10/20/30/50）发现**毫无差异**，逼出真凶：**全量 SQL 日志**。
关掉后 1387/s。教训：**大优化后不要凭"看起来像"归因，要对照实验**。

### Bug 2：缓存一致性脏读
r3 复现：线程 A 更新 DB 后删缓存；线程 B 并发回填了**旧值**，导致缓存与 DB 不一致
（`stale=true`）。用**延迟双删**修复（`stale=false`）。

### Bug 3：限流被 ZSet member 撞车绕过
v4 限流设定 500/s，实测放行 **1370/s**。根因：`math.randomseed(now)` 用毫秒时间戳播种，
**同毫秒请求生成相同 member**，被 ZSet 去重 → `ZCARD` 少算 → 限流失效。
修复（member 改由调用方传 UUID）后放行 **512/s ≈ 500/s**。

### 附带：Kafka 故障静默丢单
停 Kafka 时，接口**返回成功**但订单永不落库。加发送失败回调 + 缩短超时后，
变成**明确失败 + Redis 回滚**，不再静默（详见 `fault-injection.md`）。

## 7. 关键技术点速查（面试用）

- **N+1**：识别（trace）、批量 IN、`IN` 分批、MyBatis `<foreach>`。
- **连接池**：`HikariCP` 参数、`connection-timeout`、公式 `核数*2+磁盘`、"不是越大越好"。
- **SQL 日志**：`StdOutImpl` 的隐藏开销（14x），压测要关。
- **缓存**：Cache-Aside、缓存一致性（延迟双删 / binlog / 短 TTL）、穿透击穿雪崩。
- **异步**：`@Async` 线程池参数、拒绝策略（CallerRuns 背压）、`@Async` 失效场景。
- **秒杀防超卖**：`UPDATE ... WHERE stock>=1`、Redis+Lua 预扣。
- **一人一单**：Redis Set 幂等、唯一索引、分布式锁（SETNX/Redisson）。
- **削峰**：Kafka 异步、LAG 监控。
- **消息可靠性**：手动 ack、幂等消费、死信、本地消息表/事务消息。
- **状态机**：支付乐观锁（条件更新）、超时关单回补。
- **限流**：滑动窗口（ZSet）、令牌桶、AOP 注解、维度（IP/USER/METHOD）。
- **故障注入**：明确降级 vs 静默失败。

## 8. 已知不足 / 可继续

- 单机压测（应用+JMeter 同机），结论只做相对对比。
- 生产端未做本地消息表/事务消息；消费者死信队列未做。
- 应用启动对 Kafka 强依赖（Kafka 不在会卡启动）。
- 库存分桶（附录 A）、缓存穿透/击穿/雪崩未覆盖。
- 限流维度单一（IP），可扩展用户/全局组合。
