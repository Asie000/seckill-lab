# r6b-multilevel-cache-hardened —— 多级缓存加强实验（补 r6 的短板）

**tag**：`r6b-multilevel-cache-hardened`
**日期**：2026-10-10
**主题**：修正 `r6` 的测试不足——补上 **Redis 真实负载**、**工作集/L1 容量**、**一致性验证**。
**标准口径**：日志关闭；单机，相对对比。

---

## 0. 为什么有这一版（r6 的问题）

`r6` 只压了 **一个商品 id**、且请求**全程命中缓存**，因此：

1. 只证明了「L1 命中比 L2 命中快 ~1.6x」，**没压到 DB、没量 Redis 真实负载**；
2. 文档里说的「Redis 请求量降到个位数」是**应用内 `l2Hits` 计数器推算**的，不是 Redis 说的；
3. 文档写了「更新后保证不脏读」——**没验证过，而且是错的**（见实验 3）。

本版把这三项补上，结论以 **Redis 自身统计** 与 **实际竞态复现** 为准。

---

## 实验 1：Redis 真实负载（来自 Redis 自身）

**方法**：跑压测前后读 `redis-cli INFO commandstats` 的 `cmdstat_get:calls`，取差值。
**基线**：空转 10s，Redis GET 增量 = **0**（无背景流量，测量可信）。

**工作集**：随机 `goods_id` 1~21（21 个商品，均匀访问，已验证每个 ~54500 次）。
**每档**：30s；`ml=多级` vs `redis=仅Redis`。

| 模式 | 并发 | 吞吐 | 平均 | P99 | **真实 Redis GET** | GET/请求 |
|---|---:|---:|---:|---:|---:|---:|
| 多级 | 100 | 51017/s | 1.6ms | 5 | **126** | 0.0001 |
| 多级 | 200 | 46376/s | 3.6ms | 9 | **126** | 0.0001 |
| 多级 | 500 | 46230/s | 9.0ms | 19 | **126** | 0.0001 |
| 多级 | 1000 | 32587/s | 24.9ms | 272 | **126** | 0.0001 |
| 仅 Redis | 100 | 33068/s | 2.5ms | 6 | 990393 | 1.0000 |
| 仅 Redis | 200 | 27520/s | 6.0ms | 14 | 824020 | 1.0000 |
| 仅 Redis | 500 | 30736/s | 13.6ms | 24 | 920483 | 1.0000 |
| 仅 Redis | 1000 | 29744/s | 28.1ms | 61 | 893449 | 1.0000 |

**结论（有 Redis 自己背书）**：
- 请求量 ~100万~150万，多级模式 Redis 只被调用 **126 次**；仅 Redis 模式是 **~90万次**。
- **Redis 负载下降约 7000~7800 倍**（126 vs ~900k），吞吐约 1.5x、P99 大幅下降。
- 附带验证：仅 Redis 模式的 `l2Hits`(990369) ≈ Redis 实测 GET(990393)，差 24 = 冷启动回源数——
  **应用计数器与 Redis 统计互相印证**。

## 实验 2：工作集与 L1 容量

把 L1 的 `maximumSize` 从 1000 降到 **5**（工作集仍是 21），看命中率与 Redis 负载：

| L1 容量 | 并发 | 吞吐 | Caffeine 报的命中率 | 真实 Redis GET | GET/请求 |
|---:|---:|---:|---:|---:|---:|
| 1000 | 500 | 46230/s | 0.9999 | 126 | 0.0001 |
| 5 | 500 | 38243/s | 0.8259 | 199204 | 0.1741 |
| 5 | 200 | 43428/s | 0.8622 | 179176 | 0.1378 |
| 5 | **1** | 5779/s | **0.2366** | 87945 | 0.7634 |

**两个发现**：

1. **容量不足 → Redis 负载暴涨**：L1 只有 5 格时，真实 Redis GET 从 126 涨到 ~18万~20万（~1500x）。
   这正是"多级缓存第一级要够大"的意义。
2. **并发会"抬高"命中率（单飞效应）**：单线程命中率 **23.66% ≈ 5/21 = 23.8%**（符合 LRU 理论）；
   但 200 线程时却是 **86.22%**。原因：Caffeine 的 `get(key, loader)` 对同一 key **单飞**，
   并发下等待同一 key 加载的线程被直接喂结果、算作 hit。**并发越高，重复回源越少**。
   > 所以：真实"回源次数"要看 **Redis 实测 GET**，不能只看缓存自报命中率。

## 实验 3：一致性（竞态复现 + 修复）

r6 声称「更新后保证不脏读」。实测发现**多级缓存在单实例下也会脏读**：

### 竞态

```
t0    reader  L1 miss，loader 从 DB 读到 old（如 7999）
t50   writer  改 DB=new(8000)，失效 L1+L2
t300  reader  才把 old(7999) 写进 L1     <-- 旧值覆盖，L1 脏了
```

**朴素失效**：`POST /api/goods/1/ml/race`

```json
{"dbPrice":8000.00, "l1Price":7999.00, "stale":true,
 "desc":"多级缓存 naive 失效：并发回填把旧值写进 L1，L1 与 DB 不一致"}
```

### 修复：延迟失效（延迟双删的本地版）

更新后先失效一次，**延迟 500ms 再失效一次**，把并发回填进 L1 的旧值清掉。
`POST /api/goods/1/ml/race-fixed`

```json
{"dbPrice":8001.00, "l1PriceAfterInvalidate":null, "readPrice":8001.00, "stale":false,
 "desc":"延迟失效：并发回填的旧值被第二次失效清除，最终一致"}
```

**结论**：多级缓存的一致性比单级更麻烦（多一层 L1 要失效）；单实例可延迟双删，
**多实例还需跨实例广播失效 L1**（本实验未实现）。

## 4. 结论与对 r6 的更正

| 项 | r6 的说法 | r6b 实测 |
|---|---|---|
| Redis 负载 | "降到个位数"（应用计数器推算） | **126 vs ~90万（Redis 实测），降 ~7000x** |
| 工作集 | 单 key，无容量影响 | 21 key；L1 容量 5 时 Redis 负载涨 ~1500x |
| 一致性 | "保证不脏读" | **单实例也会脏读**；需延迟失效/广播失效 |
| 吞吐收益 | ~1.6x | 随机工作集下 ~1.5x |

## 5. 复现命令

```powershell
# 多级（L1+L2），随机工作集，测 Redis 真实负载
scripts\app.ps1 -Action restart -NoSqlLog
scripts\ml-sweep2.ps1 -Mode ml    -Threads 100,200,500,1000

# 仅 Redis
scripts\app.ps1 -Action restart -NoSqlLog -MultiLevelOff
scripts\ml-sweep2.ps1 -Mode redis -Threads 100,200,500,1000

# L1 容量实验
scripts\app.ps1 -Action restart -NoSqlLog -L1MaxSize 5
scripts\ml-sweep2.ps1 -Mode ml -JmxTag rand5 -Threads 500

# 一致性
curl -X POST http://127.0.0.1:8081/api/goods/1/ml/race
curl -X POST http://127.0.0.1:8081/api/goods/1/ml/race-fixed
```
