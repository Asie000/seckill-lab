# 专题实验：SQL 日志开销（14 倍）

**日期**：2026-10-10
**背景**：`r2-pool` 做连接池梯度时发现 10/20/30/50 吞吐完全一样，怀疑另有隐藏瓶颈，遂做此对照。
**结论**：真正的瓶颈是 **MyBatis 的全量 SQL 日志（StdOutImpl）**。关掉它，QPS 提升 **13~20 倍**。

---

## 1. 现象怎么发现的

`r2` 的连接池梯度（200 并发）结果异常平坦：

| pool | 吞吐 | 平均 | P99 |
|---:|---:|---:|---:|
| 10 | 92.6/s | 2008ms | 2939 |
| 20 | 90.8/s | 2052ms | 2991 |
| 30 | 90.2/s | 2067ms | 3017 |
| 50 | 90.6/s | 2054ms | 2963 |

连接池翻 5 倍毫无变化 → 说明**瓶颈不在连接池**。于是去找"到底谁在卡"。

## 2. 病灶：`application-dev.yml` 里的 SQL 日志

```yaml
mybatis-plus:
  configuration:
    log-impl: org.apache.ibatis.logging.stdout.StdOutImpl
```

这条配置让 MyBatis 把**每一条 SQL 打印到 stdout**（`Preparing: SELECT ...`）。
它本身是开发调试用的，但在压测时，每秒上千条 SQL 的打印 + flush + 同步写，成了压倒性的开销。

**关掉方法**（运行时覆盖，不改 yml）：

```
--mybatis-plus.configuration.log-impl=org.apache.ibatis.logging.nologging.NoLoggingImpl
```

## 3. 对照数据（同一接口、同一并发 200）

| 版本 | 日志 ON | 日志 OFF | 倍数 |
|---|---:|---:|---:|
| r0（N+1，62 条 SQL/请求） | 20.8/s | **424.3/s** | **20.4x** |
| r1（批量，5 条 SQL/请求） | 95.7/s | **1387.3/s** | **14.5x** |
| r2（pool 30） | 95.7/s | **1288.4/s** | **13.5x** |

- 延迟同步改善：r1 日志 ON 平均 1946ms → OFF **132ms**。
- **每请求 SQL 条数越多，日志惩罚越重**（r0 的 20x > r1 的 14x），符合"按行打印"的直觉。

## 4. 为什么要做成专题

1. 它一度**掩盖了所有优化之间的差异**：日志 ON 时 r0/r1/r2 全被压到 ~20~100/s，
   连接池、N+1 的真实效果都测不准。
2. 它是个**反直觉**的发现：谁会把"打印日志"当成性能瓶颈？但数据就是 14 倍。
3. 面试价值高：体现"不靠猜、用对照实验定位瓶颈"。

> **教训**：一次大优化（N+1）之后看到吞吐涨了，不要急着把新瓶颈归因给"看起来像"的连接池。
> 用梯度实验验证，才知道真正卡在哪里。

## 5. 后续标准口径

从本专题起，**所有版本横向对比的压测统一关闭 SQL 日志**（`-NoSqlLog`），
以测出"接口本身"的性能。日志 ON 的数据作为本专题保留。

- 工具：`scripts/bench.ps1` / `app.ps1` / `pool-sweep.ps1` 均支持 `-NoSqlLog`。
- 开发调试时日志照常开启，不受影响。
